Problema 1 · T1

La pirámide de una planta embotelladora

Una embotelladora tiene: sondas de nivel en los depósitos, variadores en las cintas, un PLC S7-1500 por línea, un puesto de operador con WinCC, un sistema que lanza las órdenes de fabricación y controla los lotes, y SAP para compras y facturación. Ubica cada elemento en la pirámide, indica el tiempo de respuesta de cada nivel y la red que une cada par de niveles.

1Ubicar los elementos
NivelElementoTiempo
1 · Camposondas de nivel, variadoresµs – ms
2 · ControlPLC S7-1500ms – s
3 · SupervisiónWinCC (SCADA/HMI)s – min
4 · Operaciónel sistema de órdenes y lotes: un MESmin – h
5 · GestiónSAP: un ERPh – días
2Las redes entre niveles
  • Campo ↔ control: PROFINET (o PROFIBUS en una instalación antigua). Necesita ciclos de pocos ms.
  • Control ↔ supervisión: Ethernet con OPC UA (o el protocolo propio de Siemens).
  • Supervisión ↔ MES ↔ ERP: red de información TCP/IP, con OPC UA, bases de datos o APIs REST.
3Lo que suma puntos

Dibujar la pirámide, no solo la tabla; escribir el tiempo de respuesta de cada nivel; y explicar en una frase que la información sube y las órdenes bajan.

Problema 2 · T3

Construir y leer una trama MODBUS RTU

a) Escribe la trama con la que el maestro lee 10 registros de mantenimiento (holding) a partir de la dirección 0 del esclavo 1. b) ¿Cuántos bytes tendrá la respuesta? c) Escribe la trama que pone el valor 3 en el registro 1 del esclavo 17.

1a) Trama de lectura

Esclavo 01, función 03 (leer holding registers), dirección inicial 00 00, cantidad 00 0A, y el CRC-16 con el byte bajo primero:

01 03 00 00 00 0A C5 CD

2b) Tamaño de la respuesta

Esclavo (1) + función (1) + número de bytes (1, que vale 20 = 0x14) + 10 registros × 2 bytes (20) + CRC (2) = 25 bytes. Empieza por 01 03 14.

3c) Trama de escritura

Esclavo 17 = 0x11, función 06 (escribir un registro), registro 00 01, valor 00 03:

11 06 00 01 00 03 9A 9B

La respuesta correcta a una función 06 es el eco de la petición.

Problema 3 · T3

¿Quién gana el bus CAN?

Tres nodos empiezan a transmitir a la vez con identificadores 0x120, 0x0F5 y 0x121. ¿Cuál gana y en qué bit se decide? ¿Qué pasa con los otros?

1Pasar a binario (11 bits)
IDDecimalBinario
0x120288001 0010 0000
0x0F5245000 1111 0101
0x121289001 0010 0001
2Comparar bit a bit desde el más significativo

Los bits 10 y 9 son 0 en los tres. En el bit 8, 0x0F5 envía un 0 (dominante) y los otros dos un 1 (recesivo): leen un 0 en el bus y se retiran. Gana 0x0F5, el identificador más bajo.

3Qué pasa después

Los perdedores reintentan cuando el bus queda libre. Entre 0x120 y 0x121 la diferencia está en el último bit, así que ganará 0x120. Nadie pierde su mensaje: el arbitraje es no destructivo.

Problema 4 · T10

¿Caben estas tareas? Rate Monotonic

Un controlador ejecuta tres tareas periódicas con prioridades fijas: τ1 (C = 1 ms, T = 4 ms), τ2 (C = 2 ms, T = 6 ms) y τ3 (C = 3 ms, T = 12 ms). El plazo de cada una es su periodo. ¿Son planificables con Rate Monotonic?

1Prioridades

Rate Monotonic da más prioridad al periodo más corto: τ1 > τ2 > τ3.

2Prueba de Liu y Layland

U = 1/4 + 2/6 + 3/12 = 0,250 + 0,333 + 0,250 = 0,833. La cota para 3 tareas es 3·(21/3 − 1) = 0,780. Como 0,833 > 0,780, la prueba no lo garantiza, pero tampoco dice que falle (U < 1). Hay que calcular los tiempos de respuesta.

3Análisis de tiempos de respuesta

Para cada tarea se itera R = C + Σ ⌈R/Tj⌉·Cj sobre las más prioritarias:

  • τ1: R = 1 ms ≤ 4.
  • τ2: R = 2 + ⌈R/4⌉·1 → 2, 3, 3. R = 3 ms ≤ 6.
  • τ3: R = 3 + ⌈R/4⌉·1 + ⌈R/6⌉·2 → 3, 6, 7, 9, 10, 10. R = 10 ms ≤ 12.

Las tres cumplen: es planificable, aunque la cota de utilización no lo asegurase. Con C3 = 4 ms la respuesta de τ3 sería 11 ms y todavía cumpliría.

Problema 5 · T8

Prueba de modificación de código: alarmas en un sensor

Se da una clase abstracta Sensor con leer() virtual pura y una derivada SensorNivel. Modifícala para que cada sensor tenga un límite mínimo y máximo y un método enAlarma() que diga si la lectura está fuera de rango. El sensor de nivel debe alarmar por debajo del 10 % y por encima del 90 %.

1Dónde va cada cambio

Los límites y enAlarma() son comunes a todos los sensores: van en la clase base, no en cada derivada. enAlarma() llama a leer(), que por ser virtual ejecutará la versión de cada sensor (polimorfismo). Los límites se pasan por el constructor y la derivada los fija en su lista de inicialización.

2Solución

C++

#include <iostream>
#include <string>

// Prueba de modificación: añadir límites de alarma a la clase Sensor
class Sensor {
public:
    Sensor(std::string nombre, double minimo, double maximo)
        : nombre_(std::move(nombre)), min_(minimo), max_(maximo) {}
    virtual ~Sensor() = default;
    virtual double leer() const = 0;
    bool enAlarma() const {                       // NUEVO
        const double v = leer();
        return v < min_ || v > max_;
    }
    const std::string& nombre() const { return nombre_; }
private:
    std::string nombre_;
    double min_, max_;                            // NUEVO: límites de alarma
};

class SensorNivel : public Sensor {
public:
    SensorNivel(std::string n, double v) : Sensor(std::move(n), 10.0, 90.0), v_(v) {}
    double leer() const override { return v_; }
    void simular(double v) { v_ = v; }
private:
    double v_;
};

int main() {
    SensorNivel lt("LT-301", 72.4);
    for (double v : {72.4, 95.0, 5.0}) {
        lt.simular(v);
        std::cout << lt.nombre() << " = " << v << " % -> "
                  << (lt.enAlarma() ? "ALARMA" : "normal") << "\n";
    }
}

Salida (compilado y ejecutado): 72.4 % -> normal, 95 % -> ALARMA, 5 % -> ALARMA.

3Lo que miran en la prueba
  • Que compila y hace lo pedido.
  • Que el cambio está en el sitio correcto (la base) y no duplicado.
  • Que entiendes el código que tocas: es una prueba de autoría. Te pueden pedir que expliques cada línea.

Problema 6 · T9

Una HMI de nivel en Qt

Una aplicación Qt recibe el nivel de un tanque con la señal nivelCambiado(double) de un objeto LectorOpcUa que vive en otro hilo. Haz que una QProgressBar muestre el nivel, que una etiqueta de alarma aparezca en rojo por encima del 90 % y que cada alarma quede registrada con su hora.

1La conexión entre hilos

El lector está en otro hilo, así que la conexión será en cola automáticamente: el slot se ejecuta en el hilo de la GUI y se pueden tocar los widgets sin peligro. No hace falta ningún mutex.

2Código

C++

// En el constructor de MainWindow
connect(lector, &LectorOpcUa::nivelCambiado, this, &MainWindow::mostrarNivel);

// Slot de MainWindow (declarado en la sección "private slots:" de la clase)
void MainWindow::mostrarNivel(double nivel)
{
    ui->barraNivel->setValue(qRound(nivel));
    const bool alarma = nivel > 90.0;
    if (alarma && !enAlarma_) {                    // solo al entrar en alarma
        ui->etiquetaAlarma->setStyleSheet("color: white; background: #c62828;");
        ui->registro->appendPlainText(
            QDateTime::currentDateTime().toString("hh:mm:ss") +
            "  ALARMA nivel alto: " + QString::number(nivel, 'f', 1) + " %");
    }
    ui->etiquetaAlarma->setVisible(alarma);
    enAlarma_ = alarma;                            // bool enAlarma_ = false; en la clase
}
3Por qué así
  • La alarma se registra al entrar en ella, no en cada lectura: si no, el registro se llena con la misma alarma.
  • Siguiendo la ISA-101, el rojo se usa solo para la alarma; la barra en estado normal va en gris.

Problema 7 · T10

Un interbloqueo en la línea

Dos hilos modifican la bomba y la válvula de una línea, cada una protegida por su mutex. El hilo A bloquea mBomba y luego mValvula; el hilo B bloquea mValvula y luego mBomba. De vez en cuando la aplicación se queda colgada. ¿Por qué? Corrígelo.

1Diagnóstico

Es un interbloqueo: A tiene la bomba y espera la válvula; B tiene la válvula y espera la bomba. Se cumplen las cuatro condiciones de Coffman, y la que podemos romper es la espera circular.

2Corrección

Pedir los cerrojos siempre en el mismo orden, o pedirlos a la vez con std::scoped_lock, que usa un algoritmo que evita el interbloqueo:

C++

#include <iostream>
#include <mutex>
#include <thread>

std::mutex mBomba, mValvula;
int bomba = 0, valvula = 0;

// Los dos hilos piden los cerrojos en el MISMO orden: nunca hay espera circular.
// std::scoped_lock (C++17) bloquea varios mutex a la vez sin riesgo de interbloqueo.
void arrancarLinea()  { for (int i = 0; i < 100000; ++i) { std::scoped_lock l(mBomba, mValvula); ++bomba; ++valvula; } }
void pararLinea()     { for (int i = 0; i < 100000; ++i) { std::scoped_lock l(mBomba, mValvula); --bomba; --valvula; } }

int main() {
    std::thread a(arrancarLinea), b(pararLinea);
    a.join(); b.join();
    std::cout << "bomba = " << bomba << ", valvula = " << valvula << "\n";   // 0 y 0
}

Salida (compilado y ejecutado): bomba = 0, valvula = 0, sin quedarse colgado.

3En Qt

Lo mismo con QMutexLocker, respetando el orden. Y mejor aún: si un dato solo lo toca un hilo y los demás le mandan señales en cola, no hace falta ningún mutex.

Problema 8 · T12

Diseñar los nodos ROS2 de una célula

Una célula tiene un PLC (accesible por OPC UA) que controla un tanque, un brazo robótico y una HMI en Qt. Diseña los nodos, topics, servicios y acciones para que la HMI muestre el nivel, pueda pedir vaciar el tanque y pueda mandar el brazo a una posición viendo su progreso.

1Nodos
  • /plc_bridge: cliente OPC UA del PLC; traduce entre OPC UA y ROS2.
  • /brazo_controller: controla el robot.
  • /hmi: la aplicación Qt con un nodo rclcpp dentro.
2Comunicaciones
QuéTipoNombre y mensajePor qué
Nivel del tanqueTopic/tanque/nivel · std_msgs/Float64Dato continuo; puede haber varios interesados
Vaciar tanqueServicio/tanque/vaciar · std_srvs/TriggerOrden puntual con confirmación
Mover el brazoAcción/brazo/ir_a · acción propia con la posiciónTarea larga con progreso y cancelación
3QoS e integración con Qt

El nivel, con best effort y depth pequeño si llega muy a menudo (si se pierde uno, llega otro), o reliable si es lento. En la HMI, rclcpp::spin() va en un hilo aparte y los callbacks emiten señales Qt hacia la interfaz.

Problema 9 · T14

Llevar los datos de la planta a la nube

Una planta tiene 500 variables. La dirección quiere un cuadro de mando en la nube. Un técnico propone leerlas todas cada segundo y subirlas. De media, cada variable cambia 2 veces por minuto. Calcula el tráfico de la propuesta y propón una alternativa.

1Tráfico de la propuesta

500 variables × 1 lectura/s = 500 valores/s, unos 43 millones al día, la mayoría repetidos.

2Alternativa

Una pasarela edge se suscribe por OPC UA a los cambios del PLC y los publica por MQTT a un broker en la nube: 500 × 2/60 ≈ 16,7 valores/s, unas 30 veces menos. La pasarela además puede agregar (medias por minuto) y seguir guardando datos si se cae internet.

Problema 10 · T14

Segmentar la red de una fábrica

En una fábrica, los PLC, el SCADA, los ordenadores de oficina y el acceso remoto del integrador están en la misma red plana. Propón una arquitectura más segura.

1Zonas
  • Zona de campo y control: PLC, variadores, E/S.
  • Zona de supervisión: SCADA, historiador, puestos de operador.
  • DMZ industrial: servidores que comparten datos con la oficina (réplica del historiador, servidor de acceso remoto, actualizaciones).
  • Zona de empresa: oficina, ERP, internet.
2Conductos

Entre zonas solo se permite el tráfico necesario, a través de cortafuegos. Ningún equipo de oficina habla directamente con un PLC: los datos suben a la DMZ y de ahí se leen. El integrador entra por VPN a la DMZ y de ahí, con autorización y registro, a lo que necesite.

3Medidas adicionales

OPC UA con SignAndEncrypt, cuentas individuales con mínimo privilegio, inventario de activos y copias de seguridad de los programas de los PLC. Es el modelo de zonas y conductos de la IEC 62443 con defensa en profundidad.
